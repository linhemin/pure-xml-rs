## 观察（给 M4 参考，M1 不阻断）

1. purexml 比 DOM 解析器 roxmltree 慢 3–4.7 倍，比 quick-xml 慢 5.5–22 倍。即使 roxmltree 要建整棵树，purexml 也更慢，说明开销主要在逐字节处理上，不是安全检查固有的成本。
2. 文本密集形态差距最大：吞吐只有约 83 MiB/s，而 roxmltree 是 263 MiB/s。初步判断是文本逐字符做码点校验和换行规范化，没有走 `memchr` 式的快速路径（库没有运行时依赖，可以自己实现 SWAR 或按字节表扫描）。
3. 属性密集形态最慢：28 MiB/s。每个开始标签都会建两个 `HashSet<(Option<String>, String)>` 去重集合，并对每个属性名和命名空间 URI 做 `to_string()`（与 D13 是同一处代码）。改成借用切片加小向量线性比较，应该能同时改善性能和 D13。
4. 1 KB 与 1 MB 的吞吐基本一致，没有发现随规模变差的情况（这里不含命名空间密集的输入，那种情况见 D10）。

更新方法：重跑 bench，替换上表，并记下提交号和环境。M4 再加 100 MB 档和“安全限制开销 ≤ 5%”门槛。
